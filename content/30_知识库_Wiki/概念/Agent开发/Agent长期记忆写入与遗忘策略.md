# Agent长期记忆写入与遗忘策略

## 先区分几种记忆

我会把记忆拆开看，不会把所有历史都叫 memory：

| 类型 | 例子 | 主要用途 |
|---|---|---|
| 工作记忆 | 当前任务的变量、工具结果、待办 | 支撑这一轮执行 |
| 情节记忆 | 某次任务发生了什么 | 回顾过去运行 |
| 语义记忆 | 已确认的稳定事实 | 跨任务复用 |
| 用户偏好 | 用户喜欢的输出格式、默认选择 | 个性化交互 |

工作记忆更像运行状态，长期记忆才需要认真考虑写入和遗忘。

## 什么内容值得写入

我会把写入门槛设得比较高，通常同时满足以下几项才保存：

- 后面大概率还会用到。
- 不是只对当前任务有效的临时信息。
- 内容已经被用户确认，或有明确证据。
- 不涉及不必要的敏感信息。
- 有时间、范围和适用对象。

模型“猜测用户可能喜欢某种方式”不能直接写成用户偏好。推断和事实必须分开存。

## 记忆对象

```ts
type Memory = {
  id: string
  kind: "fact" | "preference" | "episode"
  content: string
  scope: "user" | "workspace" | "project"
  confidence: "low" | "medium" | "high"
  createdAt: string
  updatedAt: string
  expiresAt?: string
  sourceEventId?: string
}
```

`scope` 很重要。某个项目里的约定不能自动升级成用户全局偏好。

## 冲突和更新

同一事实出现冲突时，不要简单 append 两条都保留。可以按下面的顺序处理：

1. 先判断是不是不同时间或不同范围。
2. 优先使用更新、明确、权限足够的事实。
3. 保留变更记录，但给当前检索结果一个明确版本。
4. 无法判断时询问用户，不要让模型自行拍板。

## 遗忘不是删除按钮

记忆需要有生命周期：

- 临时任务状态：任务结束后清理。
- 短期偏好：一段时间没有使用就降低权重。
- 稳定事实：可以长期保存，但仍允许用户修改和删除。
- 敏感内容：默认不保存，或者设置更短 TTL。

检索时也可以做“软遗忘”：过期、低置信度、很久没使用的记忆先不放进上下文，而不是立刻物理删除。

## 用户控制

用户应该能知道 Agent 记住了什么，并能：

- 查看记忆。
- 修改记忆。
- 删除单条或全部记忆。
- 禁止某类信息写入。
- 区分当前会话记忆和长期记忆。

没有这些控制时，所谓个性化很容易变成不可解释的行为漂移。

## 和 RAG 的区别

RAG 解决的是“去外部知识里找什么”；长期记忆解决的是“哪些关于用户、任务和历史运行的内容值得跨轮次保留”。两者都可能使用向量检索，但数据生命周期和权限边界不同。

## 面试表达

我会先把工作记忆、情节记忆、语义事实和用户偏好分开，再设置写入门槛、scope、置信度和 TTL。模型推断不能直接变成事实，冲突要有版本处理，用户还应该能查看、修改和删除记忆。Memory 负责保存，检索负责找回，上下文工程负责决定这一轮真正给模型看什么。
