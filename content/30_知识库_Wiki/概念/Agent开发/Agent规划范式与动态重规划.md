# Agent规划范式与动态重规划

## 我对规划的理解

规划不是让模型先写一篇很长的计划，而是把一个大目标拆成一组能检查、能推进、能失败的子目标。

比如“完成一个前端页面”不能直接作为一个步骤。更适合拆成：

1. 明确页面输入和验收条件。
2. 找到现有路由、组件和接口。
3. 先完成主流程。
4. 补错误态、加载态和空状态。
5. 运行检查并修复问题。

这样做的好处是每一步都有产物，Runtime 也能知道 Agent 到底有没有进展。

## 三种常见方式

### ReAct

模型边观察边行动：

```text
观察 -> 决定下一步 -> 调工具 -> 读取结果 -> 再决定
```

它适合探索性任务，遇到新信息可以马上调整。缺点是容易走弯路，工具调用次数和成本也不太好预测。

### Plan-and-Execute

先生成计划，再按计划执行。任务结构比较清楚时效率不错，但计划如果过早固定，后面一旦发现关键假设错了，就会变成“照着错误计划继续做”。

### 外层 Workflow + 内层 Agent Loop

我更倾向于这个组合：外层把任务分成确定的阶段，阶段内部只给 Agent 一小块自主空间。

例如：

```text
准备上下文 -> Agent 分析 -> 生成修改 -> 自动检查 -> 人工确认 -> 发布
```

模型可以决定“怎么分析”和“改哪些文件”，但不能决定绕过检查直接发布。

## 什么时候需要重规划

以下情况出现时，我会让 Agent 停下来重新规划，而不是继续沿着旧计划执行：

- 关键文件、接口或数据并不存在。
- 工具返回结果和原来的假设冲突。
- 连续几次尝试没有产生有效变化。
- 用户改变了目标或验收标准。
- 剩余时间、token 或调用预算不够完成原计划。
- 当前路径需要更高权限或人工确认。

重规划时要保留已经确认的事实，不能每次都把任务重置成一张白纸。

## 计划项应该长什么样

计划项最好接近结构化状态，而不是一段自然语言：

```ts
type PlanStep = {
  id: string
  goal: string
  dependsOn: string[]
  status: "pending" | "running" | "done" | "blocked"
  evidence?: string[]
  acceptance?: string[]
}
```

至少要能回答三个问题：

- 这一项完成了吗？
- 凭什么说完成了？
- 如果失败，下一步是重试、换方案还是请求用户？

## 我会加的两个保护

第一是进展检测。连续几轮只改参数、重复读同一个文件，通常不算进展。

第二是完成校验。模型说“已经完成”只能作为信号，不能作为最终依据。测试、schema 校验、文件存在性、数据库状态等确定性检查更可靠。

## 常见失败方式

- 计划写得很漂亮，但没有任何可验证产物。
- 每次遇到错误都从头规划，导致已经完成的工作被覆盖。
- 计划项太大，执行到一半无法判断卡在哪里。
- 为了追求自主性，把所有阶段都交给模型决定。
- 没有预算和终止条件，最后变成重复调用工具。

## 面试表达

我会把规划看成 Runtime 的状态，而不是只放在 prompt 里的文字。简单任务可以直接 ReAct，结构清楚的任务可以先规划再执行；更复杂的系统则用外层 Workflow 控阶段，内层 Agent Loop 负责局部决策。只要关键假设失效、没有进展、预算不足或风险升高，就应该触发重规划或暂停。
