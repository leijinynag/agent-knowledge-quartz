# Agent可观测性三支柱与轨迹调试

## 一句话定义

Agent 可观测性要把一次任务从输入到最终结果的完整轨迹结构化记录下来，并同时回答“运行是否健康”和“任务是否做对”。

## 三个基础支柱

### Metrics

用于观察系统总体趋势：

- 任务成功率、失败率和超时率。
- 首 token 延迟、总延迟和每一步延迟。
- 模型调用次数、token、费用。
- 工具成功率、重试次数和平均执行时间。
- 上下文长度、压缩次数和并发连接数。

### Traces

用于还原单次 run：

```text
run
  -> turn
    -> model span
    -> tool call span
    -> tool result span
    -> state change
  -> final
```

建议至少携带 `runId`、`turnId`、`toolCallId`、时间戳、状态和父子关系，便于从一次失败定位到具体模型决策或工具执行。

### Structured Logs

日志应记录结构化事件，而不是只打印一段拼接文本。对输入、输出、工具参数和文档内容要做脱敏，并保留版本信息，例如 prompt 版本、模型版本、工具 schema 版本和知识库快照。

## 健康指标与质量指标要分开

- 健康指标：延迟、错误率、吞吐、连接数、资源使用。
- 质量指标：答案正确性、证据覆盖、工具选择、约束遵守、任务完成度。

服务响应 200 不代表 Agent 完成了任务；最终文本看起来合理，也不代表工具选择和权限行为正确。

## 轨迹评估

一次评估至少覆盖四层：

1. 结果：是否满足验收条件。
2. 轨迹：是否选择正确工具、参数和步骤。
3. 运行：成本、延迟、重试和上下文增长。
4. 安全：是否越权、泄露敏感信息或跳过确认。

测试集不能只有 happy path，还应包含边界、工具故障、超时、限流、提示注入和线上历史失败样本。

## 失败排查流程

1. 先按 `runId` 找到完整轨迹。
2. 定位第一次偏离预期的不变量，而不是只看最终错误。
3. 区分模型决策错误、工具实现错误、上下文错误和外部系统错误。
4. 判断是否可以重放；重放时固定模型、工具和知识库版本。
5. 将脱敏后的失败轨迹加入回归集。

## 设计提醒

- 不要把完整 prompt、用户隐私和 secret 无条件写入日志。
- 不要只记录最终文本，必须记录工具调用和状态变化。
- 不要用“与参考轨迹完全一致”作为唯一标准；开放任务可能有多条正确路径。
- 对模型评分设置明确 rubric，并用人工样本校准。
