# Agent风险分级与人工审批

## 我的基本分级

我不会按“工具名字听起来危险不危险”来判断，而是看动作的实际影响：

| 等级 | 特征 | 例子 | 默认策略 |
|---|---|---|---|
| L0 | 只读、无外部影响 | 搜索文档、读取配置 | 自动执行 |
| L1 | 可逆、影响范围小 | 修改草稿、创建临时文件 | 自动执行并记录 |
| L2 | 会影响他人或外部系统 | 发消息、提交代码、修改共享数据 | 执行前确认 |
| L3 | 不可逆或高损失 | 删除数据、付款、生产发布 | 强制审批或禁止 |

这个分级应该和用户、资源、环境一起判断。同一个“写文件”工具，在临时目录和生产目录不是一个风险等级。

## 审批应该卡在哪里

审批不能只问一句“要不要继续”。真正有用的时机是：Agent 已经生成了具体动作和参数，但动作还没有执行。

确认界面至少展示：

- 要调用哪个工具。
- 会作用于哪个对象。
- 具体参数或变更摘要。
- 影响哪些人或资源。
- 是否可撤销。
- 不批准会怎样。

用户确认的是具体动作，不是模糊的“整个任务”。

## Approval Token

确认结果不能只保存成一个 `approved: true`。我会让审批绑定到动作快照：

```ts
type Approval = {
  userId: string
  toolName: string
  argsHash: string
  capability: string
  expiresAt: string
  decision: "approved" | "rejected"
}
```

如果工具名、参数、目标资源或权限发生变化，就必须重新审批。审批也应该有过期时间，不能被后续完全不同的动作复用。

## 为什么不能只相信模型

模型可以提出动作，但它不应该拥有授权本身。权限检查、风险评估和审批都要在模型之外执行，至少放在 Runtime 或工具网关层。

尤其是以下场景：

- 工具结果诱导 Agent 越权。
- 用户输入里夹带了外部指令。
- Agent 重规划后改变了目标对象。
- 长时间等待后原来的审批已经失效。

## 失败后的处理

- 用户拒绝：记录原因，停止该动作或换成只读方案。
- 审批超时：回到等待状态，不要自动当成同意。
- 参数变化：重新展示并重新审批。
- 执行中取消：根据工具能力走取消、回滚或状态查询。

## 面试表达

我会按只读、可逆、会影响外部系统、不可逆四类动作做风险分级。审批发生在具体参数生成之后、真正执行之前，并且 approval token 绑定用户、工具、参数哈希、权限和过期时间。模型只能提出动作，不能自己授予权限；重规划或参数变化后必须重新审批。
