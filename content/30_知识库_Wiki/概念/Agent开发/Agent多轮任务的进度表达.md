# Agent多轮任务的进度表达

## 我的理解

Agent 的进度不能简单做成百分比。很多任务一开始就不知道总步数，模型还可能中途重规划，所以“37%”这种数字很容易骗人。

我更倾向于展示阶段、当前动作和已完成结果，而不是强行给一个精确百分比。

## 我会展示哪些进度

| 进度类型 | 适合场景 | 展示方式 |
|---|---|---|
| 阶段进度 | 规划、检索、执行、总结 | stepper |
| 当前动作 | 正在读文件、正在调用接口 | 状态行 |
| 已完成事项 | 已检查 8 个文件 | checklist |
| 工具状态 | running / failed / done | 工具卡片 |
| 等待原因 | 等待审批、等待用户补充 | 明确提示 |

Agent UI 的重点是让用户知道“它现在卡在哪里”，而不是让进度条看起来一直在动。

## 阶段可以这样拆

```text
理解任务
  -> 收集上下文
  -> 制定计划
  -> 执行工具
  -> 校验结果
  -> 汇总输出
```

但这只是默认框架，不是所有任务都必须走完整流程。简单问答不应该为了仪式感显示一堆步骤。

## 不确定进度怎么表达

我会避免虚假的精确数字，改用这些表达：

- “正在分析第 3 个文件”
- “已完成 4/7 个明确子任务”
- “正在等待工具返回”
- “任务仍在后台运行”
- “计划已调整，新增 2 个检查点”

如果后端能提供总量，比如批量处理 100 条记录，那可以显示百分比；如果总量不确定，就显示阶段和当前动作。

## 和 RuntimeEvent 的关系

进度最好由事件归并出来：

```text
plan_created -> 展示计划
step_started -> 当前步骤高亮
tool_started -> 工具卡片 running
tool_finished -> 步骤产出更新
step_failed -> 展示可恢复错误
plan_revised -> 标记计划调整
```

前端不要自己猜 Agent 在第几步，应该消费后端明确事件。

## 常见失败方式

- 强行显示百分比，但百分比和真实状态没关系。
- 只显示“思考中”，用户不知道是否卡住。
- 计划调整后旧进度还在，用户以为任务倒退。
- 工具失败没有反映在进度里。
- 等待用户确认时还显示运行中，用户不知道需要自己操作。

## 面试表达

我不会给 Agent 多轮任务强行做精确百分比，而是展示阶段、当前动作、已完成事项、工具状态和等待原因。进度由 RuntimeEvent 归并出来，计划调整时要能更新 UI。只有任务总量明确时才展示百分比，否则更适合用 stepper、checklist 和状态行表达。
