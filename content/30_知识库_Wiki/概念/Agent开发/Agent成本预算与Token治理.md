# Agent成本预算与Token治理

## 我的理解

Agent 比普通 LLM 调用更容易失控，因为它可能多轮思考、多次检索、多次调工具，还会把工具结果继续塞回上下文。如果没有预算，问题不是“贵一点”，而是可能无限绕路。

所以我会把 token 和成本预算当成 Runtime 的一等公民。

## 预算应该分层

| 层级 | 例子 |
|---|---|
| 单次模型调用预算 | max input tokens、max output tokens |
| 单个 run 预算 | 最多轮数、最多工具调用、最多总 token |
| 单个用户预算 | 每日调用量、并发任务数 |
| 单个 workspace 预算 | 团队总成本、项目限额 |
| 高风险工具预算 | 外部 API 调用次数、付费工具次数 |

只限制模型输出长度不够，Agent 真正的成本往往来自循环次数和工具结果回填。

## 上下文进入模型前要治理

我会在每轮调用前做一次 context budget check：

```text
用户目标
  + 系统指令
  + 最近消息
  + 计划状态
  + 工具结果摘要
  + 检索内容
  <= 当前模型上下文预算
```

超过预算时不要硬塞，可以按优先级处理：

1. 保留系统约束和用户目标。
2. 保留当前步骤必需信息。
3. 压缩旧消息和长工具结果。
4. 截断低相关检索内容。
5. 必要时请求用户缩小范围。

## 工具结果不能无脑塞回上下文

工具返回越长，越应该做摘要和引用：

- 搜索结果只放 top-k 和关键片段。
- 文件读取只放相关区间。
- 长日志先抽取错误片段。
- 大表格先做统计摘要。
- 原始结果保存在事件日志里，不一定都进 prompt。

上下文不是垃圾桶，能被回放保存不等于每轮都要给模型看。

## 运行中怎么止损

我会设置这些停止条件：

- 达到最大循环轮数。
- 连续几轮没有新信息。
- 工具重复调用同一参数。
- 总 token 或成本接近预算。
- 用户取消或权限不足。
- 计划已经无法推进。

到预算边界时，Agent 应该给出当前已完成内容和下一步建议，而不是直接报一个技术错误。

## 前端应该怎么展示

前端不一定要展示精确金额，但可以展示这些信号：

- 当前任务是否接近预算。
- 是否因为预算降级了模型或压缩了上下文。
- 是否需要用户确认继续扩大范围。
- 长任务是否建议拆分。

这类提示要克制，不要让用户感觉每一步都在被打扰。

## 常见失败方式

- 只设置 max tokens，不限制循环次数。
- 每次都把完整工具结果塞进上下文。
- 检索 top-k 固定，和任务复杂度无关。
- 达到预算后直接失败，不输出中间成果。
- 成本日志只看总量，无法定位是哪类任务烧钱。

## 面试表达

我会把 Agent 的 token 和成本预算放进 Runtime 设计里，不只限制单次模型输出，还限制 run 轮数、工具调用次数、总 token 和用户级配额。每轮调用前做 context budget check，长工具结果先摘要再入上下文；接近预算时降级、压缩或请求用户确认，而不是让 Agent 无限绕路。
