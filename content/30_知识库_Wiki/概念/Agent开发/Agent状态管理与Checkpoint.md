# Agent状态管理与Checkpoint

## 一句话定义

Checkpoint 是 Agent 在关键状态迁移后保存的可恢复快照，使长任务能够暂停、审批、重试和在服务重启后继续，而不是从头重复执行。

## 应保存的状态

- 任务目标、约束和验收条件。
- 当前状态与计划版本。
- 已完成和未完成步骤。
- 关键消息或压缩摘要。
- 工具调用 ID、幂等键和结果引用。
- 已获得的审批及作用范围。
- token、时间和调用预算。
- 关联的事件序号。

不要只保存 messages。工具副作用、审批和外部资源版本同样重要。

## 保存时机

- 模型完成一次决策后。
- 工具开始前和完成后。
- 等待用户输入或审批前。
- 上下文压缩后。
- 任务结束或失败时。

写入 checkpoint 与记录事件要有一致的顺序，避免状态已更新但事件缺失。

## 恢复流程

```text
读取最新 checkpoint
  → 验证任务租约
  → 对比外部资源状态
  → 确认未完成工具是否已产生副作用
  → 重建最小上下文
  → 从合法状态继续
```

超时不代表工具未执行。恢复时应先查询操作状态，再决定重试。

## 并发控制

- 同一任务只允许一个有效执行租约。
- checkpoint 使用版本号或乐观锁。
- 重复 worker 写入时拒绝旧版本。
- 用户取消状态必须高于普通继续执行。
- 审批结果绑定具体动作和参数哈希。

## Checkpoint 与 Event Log

- Checkpoint 用于快速恢复当前状态。
- Event Log 用于解释历史、审计和回放。

只用事件可以重建状态，但长任务重放成本高；只用快照无法解释发生了什么。通常两者一起使用。

## 常见失败模式

- 每个 token 都保存，写入压力过大。
- 只在任务结束保存，崩溃后无法恢复。
- 恢复时直接重试写工具，产生重复副作用。
- checkpoint 没有 schema 版本，升级后无法读取。
- 多个 worker 同时推进同一任务。

## 面试表达

我会在关键状态迁移处保存版本化 checkpoint，并用事件日志记录完整过程。恢复时先获得任务租约，再校验外部副作用和幂等状态，不会简单把最后一条消息重新发给模型。这样才能支持人工审批、服务重启和长任务续跑。
