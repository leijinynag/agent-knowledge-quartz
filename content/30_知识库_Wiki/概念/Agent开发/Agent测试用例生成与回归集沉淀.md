# Agent测试用例生成与回归集沉淀

## 我的理解

Agent 的测试不能只测最后一句回答。很多问题出在过程里：选错工具、重复调用、漏掉审批、上下文压缩后丢信息、工具失败后没有恢复。

所以我会把测试对象拆成“输入、轨迹、工具结果、最终结果”四层。

## 一个测试用例应该长什么样

```ts
type AgentEvalCase = {
  id: string
  userGoal: string
  context: unknown
  expectedOutcome: string
  expectedToolUse?: string[]
  forbiddenActions?: string[]
  rubric: string[]
  tags: string[]
}
```

其中 `expectedOutcome` 不一定是完全固定文本，更像是应该满足的结果；`forbiddenActions` 很重要，比如不能改文件、不能访问外部系统、不能跳过审批。

## 回归集从哪里来

我会从这些地方沉淀回归用例：

- 线上真实失败轨迹。
- 用户手动纠正过的回答。
- 工具调用失败但最终没有恢复的任务。
- 权限或审批边界被绕过的案例。
- 成本异常高、循环次数异常多的 run。
- 新功能上线前人工构造的关键场景。

每次修复 Agent 问题，都应该顺手把失败案例脱敏后放进回归集。

## 测什么

| 维度 | 例子 |
|---|---|
| 结果正确性 | 是否完成用户目标 |
| 工具选择 | 是否用了该用的工具 |
| 权限合规 | 高风险动作是否审批 |
| 过程效率 | 是否重复调用、是否绕路 |
| 错误恢复 | 工具失败后是否能换方案 |
| 输出质量 | 是否清楚说明限制和下一步 |

Agent 评估最好同时看 outcome 和 trajectory。只看最终回答，很容易漏掉过程中的风险。

## 自动生成测试用例要谨慎

可以让模型帮忙扩展测试输入，比如改写同义问法、补边界条件、生成异常上下文。但期望结果和通过标准最好人工审核。

我不会完全相信“模型生成的用例 + 模型自己打分”。它可以提效，但不能替代关键路径上的人工判断。

## 常见失败方式

- 只保存 prompt，不保存上下文和工具结果。
- 每次问题修完就结束，没有变成回归用例。
- 用模型当唯一裁判，评分标准很飘。
- 测试只覆盖成功路径，不覆盖权限、失败和取消。
- 评估数据混入敏感信息，没有脱敏和权限控制。

## 面试表达

我会把 Agent 回归集看成真实失败经验的沉淀。测试用例不只包含用户输入，还要包含上下文、期望结果、允许和禁止的工具行为、评分标准。每次线上失败修复后，把轨迹脱敏加入回归集；评估同时看最终结果和执行轨迹，而不是只看回答像不像。
