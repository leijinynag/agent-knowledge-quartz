# Agent会话历史与前端本地缓存

## 我的基本判断

Agent 会话历史不能完全依赖前端本地缓存。前端可以缓存 UI 快照，让刷新更快；但权威状态应该在后端，因为工具调用、审批、取消和最终状态都发生在 Runtime。

我会把本地缓存定位成“体验优化”，不是“真实状态存储”。

## 前端可以缓存什么

- 会话列表的标题、时间和摘要。
- 最近消息的渲染快照。
- 当前 runId 和 lastEventId。
- 输入框草稿。
- 折叠状态、滚动位置、选中的 tab。

不适合只放前端缓存：

- 工具执行结果的唯一记录。
- 审批结果。
- 权限判断。
- 任务是否完成。
- secret 或敏感工具参数。

## 刷新恢复流程

```text
读取本地缓存
  -> 先渲染最近 UI 快照
  -> 请求后端 session/run 状态
  -> 如果仍在运行，继续订阅事件流
  -> 用后端快照修正本地状态
```

这样用户刷新后不会白屏，也不会把过期缓存当成真相。

## 缓存失效

我会给缓存加这些失效条件：

- 用户切换账号。
- workspace 或项目切换。
- 后端 session 版本变化。
- run 已进入终态一段时间。
- 本地 schema 版本升级。

如果状态对不上，以后端为准，前端缓存只负责快速展示。

## 隐私和容量

AI 会话很容易包含敏感内容。前端本地缓存要控制：

- 最大保存条数。
- 最大单条消息长度。
- 是否允许缓存工具结果。
- 退出登录时清理。
- 私密模式下不落盘。

IndexedDB 适合较大的结构化会话缓存；localStorage 更适合小配置，不适合塞长回答。

## 常见失败方式

- 把本地缓存当成任务真实状态。
- 多账号共用缓存 key。
- 重新打开页面后重新提交最后一个 prompt。
- 缓存完整工具参数，造成隐私风险。
- 后端已经取消，前端还显示运行中。

## 面试表达

我会让后端 Runtime 保存权威会话状态，前端只缓存 UI 快照、runId、lastEventId、草稿和偏好。刷新时先用缓存快速渲染，再拉后端快照校准；如果任务还在跑，就从 lastEventId 继续订阅，避免重新执行。
