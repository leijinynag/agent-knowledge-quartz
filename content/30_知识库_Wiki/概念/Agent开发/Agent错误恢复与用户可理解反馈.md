# Agent错误恢复与用户可理解反馈

## 我会先区分错误类型

Agent 出错时，前端不能只显示“生成失败”。不同错误对应不同恢复方式。

| 错误 | 用户能做什么 | 系统能做什么 |
|---|---|---|
| 网络断开 | 等待或重新连接 | 继续订阅同一个 run |
| 模型超时 | 重试或稍后再试 | 换模型、缩短上下文 |
| 工具失败 | 修改输入或重试 | 分类错误、幂等重试 |
| 权限不足 | 授权或换目标 | 提示缺少的能力 |
| 需要确认 | 批准或拒绝 | 暂停执行 |
| 上下文不足 | 补充信息 | 请求澄清 |

错误反馈要能指导下一步，而不是只把堆栈或英文错误码暴露出来。

## 前端应该保留什么

错误发生时，我会保留：

- 用户原始输入。
- 当前 assistant 已生成的部分内容。
- 已完成工具调用。
- 失败工具和错误摘要。
- runId 和可恢复位置。

这样用户可以继续、重试或复制已有结果，而不是一次失败整段对话全没了。

## 三种重试按钮不是一回事

### 重新连接

只恢复事件流，不重新执行任务。

适合网络断开、页面刷新、SSE 连接被代理切断。

### 从失败点继续

沿用当前 run 和 checkpoint，让后端从可恢复状态继续。

适合工具临时失败、模型超时、等待用户补充信息后继续。

### 重新生成

创建新的 run，可能重新调用工具。

适合用户想换回答方式，或者旧状态已经不可恢复。对有副作用任务要特别谨慎。

## 反馈文案怎么写

我倾向于用“发生了什么 + 现在可以做什么”的结构：

```text
连接断开了，任务可能仍在后台运行。可以重新连接查看最新进度。
```

比下面这种更可用：

```text
Error: stream closed
```

但调试信息不能丢，可以放在展开区域或 timeline 里。

## 常见失败方式

- 所有错误都叫“生成失败”。
- 重试按钮实际重新执行了副作用工具。
- 用户取消被显示成系统错误。
- 工具失败时清空已经生成的文本。
- 没有 runId，页面刷新后无法恢复。

## 面试表达

我会把 Agent 错误分成网络、模型、工具、权限、审批和上下文几类。前端保留 runId、部分输出和工具状态，并区分重新连接、从失败点继续、重新生成三种动作。用户看到的是可行动反馈，调试细节放到 timeline 或展开信息里。
