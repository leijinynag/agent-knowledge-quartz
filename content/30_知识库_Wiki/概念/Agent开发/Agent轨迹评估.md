# Agent轨迹评估

## 一句话定义

Agent 轨迹评估是在检查最终结果之外，对 Agent 从目标到结果之间的决策、工具调用、状态变化、错误恢复和终止行为进行评估。

## 为什么只看最终结果不够

两个 Agent 都可能给出正确答案，但可靠性完全不同：

- 一个使用了正确工具并验证证据。
- 一个基于错误信息碰巧猜对。
- 一个用三步完成任务。
- 一个执行几十次重复调用并产生高成本。
- 一个遵守权限边界。
- 一个尝试了越权操作，只是工具最终拒绝。

因此评估必须同时覆盖结果、过程、成本和安全。

## 四层评估模型

### 结果层

- 是否满足用户目标和验收条件。
- 结果是否正确、完整、格式合规。
- 生成的文件、代码或数据是否通过确定性检查。

### 轨迹层

- 是否选择了合适的工具。
- 工具参数是否正确。
- 步骤顺序是否合理。
- 是否使用了工具返回的新信息。
- 是否出现重复调用、无效规划或过早终止。

### 运行层

- 轮数、token、延迟和费用。
- 工具成功率、重试次数和恢复时间。
- 上下文增长速度及压缩次数。
- 是否产生可回放的完整事件日志。

### 安全层

- 是否遵守权限和确认策略。
- 是否把不可信内容当成系统指令。
- 是否泄露 secret 或非任务所需数据。
- 遇到高风险或歧义时是否正确暂停。

## 评估数据结构

一次运行至少记录：

```json
{
  "goal": "用户目标",
  "expected": "验收条件",
  "events": [
    {
      "type": "model_decision | tool_call | tool_result | state_change | final",
      "timestamp": "...",
      "payload": {}
    }
  ],
  "final_output": "...",
  "metrics": {
    "turns": 0,
    "tool_calls": 0,
    "latency_ms": 0,
    "tokens": 0
  }
}
```

事件结构应与线上可观测日志一致，这样失败样本才能直接回放，而不是维护两套互不兼容的数据。

## 指标设计

| 指标 | 说明 |
|---|---|
| Task success rate | 任务达到验收条件的比例 |
| Tool selection accuracy | 工具选择是否匹配当前意图 |
| Argument accuracy | 工具参数是否正确、完整 |
| Recovery rate | 工具失败后能否恢复 |
| Constraint violation rate | 权限、格式、业务约束违规比例 |
| Excess step rate | 超出参考轨迹的无效步骤比例 |
| Cost per successful task | 每个成功任务的平均成本 |

不要把“与参考轨迹完全相同”当作唯一目标。开放任务可能存在多条正确路径，更适合检查必要节点、禁止行为和最终不变量。

## 测试集分层

- **核心集**：最常见、最重要的用户任务。
- **边界集**：缺参数、模糊目标、空结果和超长输入。
- **故障集**：超时、限流、工具异常和部分成功。
- **安全集**：越权请求、提示注入、敏感数据和确认流程。
- **回归集**：线上出现过的真实失败案例。

每次修复线上问题后，都应将该轨迹脱敏并加入回归集。

## 评估方法

- 确定性校验：schema、测试、数据库状态、文件哈希。
- 规则评分：工具白名单、调用顺序、预算、必须出现的事件。
- 模型评分：开放文本质量、推理充分性和用户意图满足度。
- 人工审核：高风险任务、评分分歧和新型失败模式。

可靠评估应优先使用确定性信号；模型评分需要明确 rubric，并用人工样本校准。

## 面试表达

评估 Agent 时，我会把单次运行保存为事件轨迹，同时评分最终结果、工具选择、参数、错误恢复、成本和权限行为。测试集包含正常路径、边界条件、工具故障、安全攻击与线上回归样本，避免只用几个 happy path 看最终文本。
