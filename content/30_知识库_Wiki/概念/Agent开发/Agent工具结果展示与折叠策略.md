# Agent工具结果展示与折叠策略

## 我的理解

Agent 调工具之后，前端不能只显示“工具调用成功”。用户真正关心的是：Agent 查到了什么、改了什么、失败在哪里，以及这些结果和最终回答有什么关系。

但工具结果通常又很长，所以 UI 要在“看得懂”和“不吵”之间做折叠。

## 我会分三层展示

| 层级 | 展示内容 | 默认状态 |
|---|---|---|
| 摘要层 | 工具名、动作、对象、状态、耗时 | 默认可见 |
| 结果层 | 关键结果、差异、命中条目、错误摘要 | 按场景展开 |
| 原始层 | 参数、原始返回、日志片段 | 默认折叠 |

用户平时看摘要层就够了，排查问题时再展开结果层和原始层。

## 不同工具结果不应该长一样

我会按工具类型做展示：

- 搜索工具：展示 query、命中数量、关键片段。
- 文件读取：展示路径、行数、是否截断。
- 文件修改：展示 diff，而不是只说成功。
- API 请求：展示方法、资源、状态码、错误摘要。
- 数据库查询：展示表名、行数、字段，不直接暴露敏感数据。
- 浏览器自动化：展示当前页面、关键动作、截图或 DOM 摘要。

工具结果是给人看的，不能把 JSON 原样堆到聊天区。

## 和最终回答的关系

我会让工具卡片和最终回答能互相定位：

```text
最终回答中的结论
  -> 引用某个 toolCallId
  -> 展开对应工具结果
  -> 查看关键证据或修改 diff
```

这样用户不需要在一堆日志里猜“这句话是从哪里来的”。

## 折叠规则

我会用这些规则决定默认展开程度：

- 只读且成功：默认折叠，只展示摘要。
- 有关键发现：展开结果层。
- 发生错误：展开错误摘要。
- 有文件修改：展开 diff。
- 高风险工具：保留审批和执行结果入口。
- 结果过长：展示前几条和“查看更多”，不要撑爆页面。

## 常见失败方式

- 每个工具调用都 append 成聊天消息，主线对话被打断。
- 完整 JSON 默认展开，用户完全不想看。
- 文件修改只显示 success，看不到改了什么。
- 工具失败被藏起来，最终回答却说已经完成。
- 没有 toolCallId，回答和工具结果无法对应。

## 面试表达

我会把工具结果做成分层卡片：摘要层默认可见，关键结果按场景展开，原始参数和返回默认折叠。不同工具用不同展示方式，比如搜索看命中、文件修改看 diff、API 看状态码。最终回答最好能关联 toolCallId，让用户能从结论追到工具结果。
