# Tool Schema设计

## 一句话定义

Tool Schema 是模型理解工具用途、调用条件、参数约束和返回语义的接口合同，设计质量会直接影响工具选择和参数准确率。

## 名称

名称应使用明确的业务动词：

- 好：`search_orders`、`preview_invoice`、`send_invoice`
- 差：`process`、`run`、`manage_data`

预览和提交要拆开，读取和修改要拆开，避免一个工具根据模糊参数执行完全不同风险的动作。

## 描述

工具描述至少说明：

- 能做什么。
- 什么时候应该调用。
- 什么时候不应该调用。
- 是否有副作用。
- 返回内容和限制。

描述不要堆背景故事，关键是让模型能区分相似工具。

## 参数

- 使用领域字段，不接受任意命令。
- 对 ID、路径、URL、枚举设置格式约束。
- 必填项不要依赖模型猜测。
- 对日期和时区使用明确格式。
- 批量参数设置最大数量。
- 高风险参数提供预览和确认。

## 返回值

统一返回：

```json
{
  "ok": true,
  "data": {},
  "meta": {
    "truncated": false,
    "next_cursor": null
  },
  "error": null
}
```

结果要明确分页、截断、部分成功和可重试状态。过大的正文应外部保存，返回摘要与引用。

## 工具集合治理

- 每个工具有负责人和版本。
- 新旧版本并存时设置弃用期。
- 用离线样本测试工具选择和参数。
- 统计被选中率、失败率和误调用率。
- 合并语义重复的工具。
- 按任务阶段动态加载候选工具。

## 常见失败模式

- 描述只写“用于查询数据”，无法区分用途。
- 参数全部是自由文本。
- 工具内部偷偷执行多个高风险动作。
- 成功响应不说明只返回了部分数据。
- 错误直接返回堆栈。
- 多个工具名称不同但能力几乎相同。

## 面试表达

我把工具 schema 当成面向模型的 API 合同。名称和描述要能区分调用条件，参数尽量使用封闭的业务类型，返回值包含状态、分页、截断和结构化错误。工具上线前会用真实任务测试选择准确率，而不只是确认接口能调用。
