# Agent开发路线

## 一句话定义

Agent 开发不是“接一个模型 API，再写一段很长的 prompt”，而是把模型放进一个受约束的执行系统中，让它能够理解目标、选择动作、调用工具、观察结果、恢复错误，并在满足验收条件后结束任务。

## 先建立正确判断

开始写代码前，先判断问题到底需要哪种形态：

| 任务特征 | 更合适的方案 |
|---|---|
| 分类、抽取、改写、摘要 | 单次模型调用 |
| 步骤固定、分支可枚举 | Workflow |
| 需要检索后生成 | RAG Workflow |
| 路径不固定，需要动态选工具 | Tool-using Agent |
| 任务很长，需要暂停、恢复和审批 | Durable Agent |
| 子任务专业性强且可并行 | 受控的多 Agent 系统 |

Agent 带来的不是免费智能，而是更高的不确定性、延迟、成本和安全风险。能用确定性代码解决的部分，尽量留在代码里。

## 第一阶段：LLM 应用基本功

这一阶段的目标是稳定地完成一次模型调用：

- 理解 system、user、assistant、tool 等消息角色。
- 会设计清晰的输入边界和输出契约。
- 使用结构化输出，而不是靠正则解析自然语言。
- 处理流式增量、取消、超时、限流和网络中断。
- 记录 token、耗时、模型版本和请求标识。
- 区分可重试错误与不可重试错误。

## 第二阶段：Tool Use

模型本身只能生成信息，工具让它能够查询和改变外部世界。需要掌握：

- 把业务能力设计为小而明确的工具。
- 用 schema 限定参数，而不是让模型拼接命令字符串。
- 校验、授权、执行和展示工具结果。
- 区分只读工具与有副作用工具。
- 设计幂等键、超时、重试和部分成功语义。
- 控制每轮暴露给模型的工具数量。

## 第三阶段：Agent Runtime

这一阶段开始处理真正的自主循环：

1. 接收目标和验收条件。
2. 构造当前步骤所需上下文。
3. 请求模型给出下一步动作。
4. 校验动作和权限。
5. 执行工具并记录结果。
6. 更新任务状态。
7. 判断完成、继续、等待或失败。

## 第四阶段：Context、Memory 与 RAG

长任务的核心不是把所有历史都塞回模型，而是构造“当前决策的最小充分上下文”：

- 稳定规则长期保留。
- 任务状态结构化保存。
- 长工具结果放在外部，只传摘要和引用。
- 外部知识按当前子目标检索。
- 用户偏好和历史经验满足条件后才写入长期记忆。
- 对过期、冲突和低置信度记忆设计淘汰策略。

## 第五阶段：协议与能力生态

当工具和数据源变多，需要把一次性适配升级为协议化接入：

- MCP 负责 Host、Client 与 Server 之间的能力发现和调用。
- Provider Adapter 隔离不同模型 API 的差异。
- Skill 把复杂任务指令按需加载。
- 多 Agent 通过结构化交接传递目标、证据和约束。

## 第六阶段：可靠性、安全与评估

Agent 能跑起来只是起点，生产可用需要：

- 把运行过程记录为 trace 和结构化事件。
- 建立正常、边界、故障、安全和回归测试集。
- 评估结果、轨迹、成本和权限行为。
- 对高风险动作做人工确认。
- 隔离不可信内容、凭证和执行环境。
- 建立故障分类、降级策略和运行手册。

## 推荐的练习项目

### 文档研究 Agent

练习检索、引用、上下文压缩、长任务进度和事实核验。验收条件可以是输出结构完整、每个结论都能追溯到证据。

### 代码仓库 Agent

练习文件检索、命令执行、补丁生成、测试、权限控制和 checkpoint。验收条件可以是测试通过且只修改允许范围内的文件。

### 客服工单 Agent

练习结构化抽取、规则路由、知识库检索、人工升级和审计。验收条件可以是分类准确、回复合规、风险工单全部升级人工。

## 面试表达

我会从单次调用和固定 workflow 开始，只有任务路径无法预先枚举时才引入 Agent。实现上先做好结构化输出和工具层，再实现受预算控制的 Agent Loop；随后补齐上下文管理、状态持久化、权限、trace 和评估。判断一个 Agent 是否成熟，不看它能演示多少能力，而看它遇到失败时是否可解释、可恢复、可降级。
