# Tool Use与函数调用

## 一句话定义

Tool Use 是模型输出结构化行动意图，由宿主系统完成校验、授权和执行，再把结果作为观察返回模型的机制。

## 模型和 Runtime 的职责

模型可以提出：

```json
{
  "tool": "search_documents",
  "arguments": {
    "query": "Agent checkpoint",
    "limit": 5
  }
}
```

Runtime 必须负责：

1. 工具是否存在。
2. 参数是否符合 schema。
3. 当前身份是否有权限。
4. 是否需要人工确认。
5. 是否超过预算或频率限制。
6. 工具在哪个隔离环境执行。
7. 结果如何裁剪、持久化和返回。

模型永远不应直接获得数据库连接、云密钥或系统 shell 的无限权限。

## 好工具的特征

- 名称能表达业务动作，例如 `get_order`，而不是模糊的 `execute`。
- 描述明确说明何时调用、何时不要调用。
- 参数使用业务字段，不让模型拼接 SQL 或 shell。
- 返回结构稳定，有状态、数据、错误和可重试信息。
- 副作用边界明确，最好把预览与提交拆成两个工具。
- 调用结果可审计，支持请求标识和幂等键。

详见：[[30_知识库_Wiki/概念/Agent开发/Tool Schema设计]]

## 工具调用循环

```text
MODEL_DECISION
  → TOOL_REQUESTED
  → SCHEMA_VALIDATED
  → POLICY_CHECKED
  → WAITING_APPROVAL（可选）
  → TOOL_STARTED
  → TOOL_SUCCEEDED / TOOL_FAILED
  → RESULT_NORMALIZED
  → MODEL_OBSERVES_RESULT
```

工具错误也应作为结构化结果返回。模型需要知道错误类型、是否可重试、哪些输入有问题，而不是只收到一段堆栈。

## 错误结果示例

```json
{
  "ok": false,
  "error": {
    "code": "RATE_LIMITED",
    "message": "查询频率过高",
    "retryable": true,
    "retry_after_ms": 1500
  }
}
```

不要把内部堆栈、数据库结构和密钥信息原样暴露给模型。

## 并行工具调用

适合并行：多个互不依赖的只读查询、搜索多个数据源、检查多个独立文件。

不适合并行：后一步依赖前一步标识、写操作竞争同一资源、调用顺序影响业务状态、需要先审批再执行。

并行不是默认优化，它会增加限流、错误聚合、取消和结果排序的复杂度。

## 副作用与确认

| 风险 | 示例 | 默认策略 |
|---|---|---|
| 低 | 搜索、读取公开信息 | 自动执行 |
| 中 | 读取私有文件、运行受限查询 | 权限检查和审计 |
| 高 | 发消息、提交代码、修改数据 | 展示预览并确认 |
| 极高 | 删除、支付、生产发布 | 强认证、双重确认或禁止 |

确认面板要展示真实影响范围，不只显示工具名。

## 幂等、超时与重试

- 只读工具通常可以安全重试。
- 写工具需要幂等键或操作状态查询。
- 超时不等于失败，远端可能已经执行成功。
- 重试前先判断是否存在部分成功。
- 为单工具和整个任务分别设置预算。

详见：[[30_知识库_Wiki/概念/Agent开发/Agent工具执行的幂等重试与超时]]

## 工具过多时怎么办

一次暴露几十个相似工具会降低选择稳定性。可以按任务阶段和权限筛选工具，先做能力检索再加载完整 schema，合并高度重复的只读工具，并对工具描述做离线选择准确率评估。

工具集合应像 API 产品一样治理，包含版本、负责人、权限、SLA、弃用策略和测试。

## 常见失败模式

- 工具名和描述过于相似，模型频繁选错。
- 参数允许自由文本，导致注入或格式错误。
- 工具结果太长，挤占上下文。
- 对写操作自动重试，产生重复副作用。
- 工具返回成功，但业务实际只完成了一部分。
- 前端只显示“正在调用工具”，用户看不到影响范围。

## 面试表达

我把模型视为行动提议者，而不是执行者。所有工具调用都经过 schema 校验、能力权限、风险审批、超时和幂等控制。工具结果会归一化为可恢复的结构化观察；工具数量也会按当前阶段裁剪，避免模型在大量相似能力中做不稳定选择。
