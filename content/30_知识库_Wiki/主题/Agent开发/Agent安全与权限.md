# Agent安全与权限

## 一句话定义

Agent 安全不是要求模型永远做出正确判断，而是通过权限、隔离、校验、审批和审计，把模型可能犯错时的影响控制在可接受范围内。

## 威胁模型

主要风险包括：

- 用户直接要求越权操作。
- 网页、邮件、文档中的提示注入。
- 工具参数被构造成命令、SQL 或路径注入。
- Agent 读取超出任务范围的数据。
- Secret 被写入 prompt、trace 或最终回复。
- 写工具重试造成重复发送、删除或支付。
- 多租户数据在检索、缓存或日志中串线。
- 第三方 MCP Server 返回恶意内容或滥用凭证。

安全设计必须覆盖输入、上下文、模型输出、工具执行和结果展示整个链路。

## 分层防线

### 输入层

- 限制大小、类型和来源。
- 将外部内容标记为不可信数据。
- 对文件、URL 和租户做作用域校验。

### 上下文层

- 系统规则与外部内容分区。
- 不把 Secret 直接放进模型可见上下文。
- 检索前执行权限过滤，而不是检索后再隐藏。

### 模型输出层

- 使用结构化输出。
- 对参数做 schema 和业务校验。
- 不把模型文本直接拼成 shell、SQL 或模板执行。

### 工具层

- 使用最小能力令牌。
- 只开放当前任务需要的工具。
- 对写操作设置幂等、审批和影响范围检查。
- 在沙箱或受限网络环境中运行高风险工具。

### 结果层

- 脱敏 Secret 和个人信息。
- 防止工具错误泄露内部堆栈。
- 输出外部内容时保留来源边界。

详见：[[30_知识库_Wiki/概念/Agent开发/Agent Guardrails分层设计]]

## 权限模型

不要只用 `admin/user` 这种粗粒度角色。工具授权应同时考虑：

```text
身份
+ 资源范围
+ 允许动作
+ 当前任务目的
+ 环境
+ 风险等级
+ 是否已有审批
```

Capability 可以表达为“允许读取仓库 A 的 issue”，而不是“拥有 GitHub token”。凭证由执行层持有，模型只看到能力描述。

详见：[[30_知识库_Wiki/概念/Agent开发/Capability-based Tool Policy]]

## Prompt Injection

提示注入无法只靠一句“忽略恶意指令”解决。更有效的策略是：

- 把外部内容当作数据，不提升其指令优先级。
- 限制外部内容能触发的工具集合。
- 关键动作依据系统策略，不依据网页文字。
- 读取和执行分离，先提取事实再决定动作。
- 对跨域数据外传、高风险工具和 Secret 访问设置硬阻断。

详见：[[30_知识库_Wiki/概念/Agent开发/Agent提示注入与不可信内容隔离]]

## Human-in-the-loop

人工确认适合不可逆、影响范围大、涉及外部承诺或模型置信度不足的动作。确认信息应包含：

- 将执行什么。
- 影响哪些资源和用户。
- 关键参数和差异预览。
- 是否可撤销。
- 为什么需要此操作。

确认不是万能开关。频繁弹窗会让用户形成机械点击，低风险动作应通过策略自动放行。

## Secret 管理

- Secret 存在服务端凭证系统中。
- 工具执行时按身份和作用域临时获取。
- 模型只知道能力，不看到真实 Secret。
- 日志记录凭证引用和授权结果，不记录明文。
- 用户输入中的 Secret 要尽早识别和脱敏。
- 第三方服务采用短期令牌和最小 scope。

## 多租户与隔离

- 所有检索、缓存、文件和 trace 带租户作用域。
- 工具执行环境不复用可泄露状态。
- 向量检索必须在召回前过滤租户和权限。
- 调试界面也要遵守数据权限。
- 删除数据时同步清理缓存、索引和记忆。

## 常见失败模式

- 只靠 prompt 声明安全规则。
- 使用一个全权限服务账号执行所有任务。
- 工具 schema 允许任意 URL、路径或命令。
- 先检索全部数据，再在回答阶段隐藏。
- 审批页面只显示“是否允许”，没有影响预览。
- Secret 出现在错误堆栈、模型输入或分析平台。
- 第三方 MCP Server 默认被视为可信。

## 面试表达

我不会把安全责任交给模型。模型只提出动作，Runtime 根据身份、资源、动作、风险和审批判断是否允许；凭证留在工具执行层，不进入 prompt。外部内容按不可信数据处理，高风险工具运行在受限环境并保留审计记录。
