# LLM应用开发

## 一句话定义

LLM 应用开发是围绕模型调用构建输入、输出、流式交互、错误处理、成本控制和质量验证的工程过程，它是 Workflow 与 Agent 的共同基础。

## 一个完整请求包含什么

```text
用户输入
  → 输入校验与安全过滤
  → 上下文构造
  → 模型与参数选择
  → 模型调用
  → 流式事件或完整结果
  → 结构校验
  → 业务后处理
  → 记录 trace、usage 和结果
```

模型调用层不应直接承担业务状态管理。它只负责把统一的内部请求转换为 Provider 请求，再把响应转换为统一事件。

## 消息与指令层级

- **稳定系统规则**：角色、权限、不可违反的约束。
- **任务说明**：本次目标、输入、验收标准和输出格式。
- **上下文证据**：文件片段、检索结果、工具结果。
- **历史状态**：已经做出的决策、未完成事项和用户偏好。

不要把不可信网页、文档或工具结果直接拼到系统规则中。外部内容应有明确边界，并声明它是数据而不是指令。

## Structured Outputs

只要输出会进入程序流程，就应该优先使用 schema：

- 信息抽取返回对象。
- 分类返回枚举。
- 计划返回步骤数组。
- 工具调用返回参数对象。
- 评估返回分数和理由。

结构化输出解决的是“语法可解析”，不自动保证“业务正确”。程序仍然要做范围、权限、实体存在性和状态一致性校验。

详见：[[30_知识库_Wiki/概念/Agent开发/Structured Outputs结构化输出]]

## Streaming

流式响应的价值不只是更快显示文字，还包括：

- 让用户看到任务正在推进。
- 实时展示工具调用、审批和阶段变化。
- 支持取消和超时。
- 让前端维护精确的运行状态。
- 将长任务从“一次黑盒请求”变成事件流。

文本增量、工具参数增量和运行状态不是同一种数据，前端应使用带类型的事件协议，而不是把所有内容都当作字符串。

## 错误处理

| 类型 | 处理方式 |
|---|---|
| 参数或 schema 错误 | 修正请求，不盲目重试 |
| 限流 | 退避、排队或切换模型 |
| 服务端暂时故障 | 有上限的重试 |
| 内容过长 | 压缩、分块、检索或切换上下文策略 |
| 流式中断 | 保留已收事件，按幂等策略续传 |
| 内容安全拒绝 | 改变业务路径或转人工 |
| 输出业务不合法 | 返回模型修复或走确定性兜底 |

重试必须有请求标识、次数上限和总时间预算，避免用户取消后后台仍持续消耗。

## 模型选择

不要用一个模型处理所有任务。可以按能力和代价分层：

- 小模型：分类、路由、简单抽取、格式修复。
- 主模型：复杂生成、规划、工具选择。
- 强模型：高难度推理、失败恢复、关键审核。
- 专用模型：向量、语音、视觉或代码任务。

模型路由必须能记录“为什么选择这个模型”，并保留失败后的升级与降级路径。

详见：[[30_知识库_Wiki/概念/Agent开发/Agent模型路由与降级]]

## Token 与缓存

成本治理不能只统计最终账单。请求前要估算固定系统指令、工具定义、会话历史、检索片段和预期输出。

稳定且重复的前缀适合 prompt caching；会频繁变化的状态应放后面。缓存命中不代表上下文设计合理，过大的稳定前缀仍会增加维护复杂度。

## Provider 抽象

不同 Provider 在消息格式、tool call、结构化输出、流式事件、usage、缓存字段和错误码方面通常不一致。

内部应定义稳定的 `ModelRequest`、`ModelEvent` 和 `ModelError`，Provider Adapter 只做协议转换，不把供应商细节扩散到 Runtime。

详见：[[30_知识库_Wiki/概念/Agent开发/Provider Adapter模型抽象]]

## 最小生产检查清单

- [ ] 输入有大小、类型和权限校验。
- [ ] 输出有 schema 和业务校验。
- [ ] 请求支持超时与取消。
- [ ] 限流和临时故障有受控重试。
- [ ] trace 中记录模型、耗时、token、缓存和错误。
- [ ] 敏感数据不会被无边界写入 prompt 和日志。
- [ ] 关键任务有离线评估集。
- [ ] 模型不可用时有降级方案。

## 面试表达

我会先把模型调用做成稳定基础设施：统一请求和流式事件、结构化输出、取消与重试、token 和 trace，再在上面构建 workflow 或 Agent。对进入业务流程的输出，我依赖 schema 加业务校验，不依赖自然语言约定；对不同 Provider，则通过 Adapter 隔离差异。
