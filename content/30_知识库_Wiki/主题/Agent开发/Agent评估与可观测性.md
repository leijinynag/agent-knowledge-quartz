# Agent评估与可观测性

## 一句话定义

Agent 评估回答“系统是否可靠完成任务”，可观测性回答“它为什么成功或失败”；两者必须共享同一套任务、事件和 trace 数据。

## 四层质量模型

### 结果质量

- 是否满足目标和验收条件。
- 输出是否正确、完整、格式合规。
- 文件、数据库或外部系统状态是否真的改变。

### 轨迹质量

- 是否选择正确工具。
- 参数是否准确。
- 是否使用了工具返回的新证据。
- 是否出现绕路、重复调用或过早结束。

### 运行质量

- 延迟、轮数、token、费用。
- 工具成功率、重试和恢复时间。
- 上下文增长和缓存命中。

### 安全质量

- 是否遵守权限和审批。
- 是否发生提示注入影响。
- 是否读取或泄露超出任务范围的数据。
- 高风险操作是否正确暂停。

## Trace 应记录什么

一次运行至少要能关联：

- `trace_id`、`task_id`、`session_id`。
- 输入目标、约束和验收条件。
- 模型请求、模型版本和 usage。
- tool call、参数摘要、结果状态和耗时。
- 状态迁移、checkpoint 和审批。
- 最终输出、错误和取消原因。

敏感参数可以脱敏或只保留哈希，但不能因为安全考虑把整个过程变成不可诊断的黑盒。

## 离线评估集

测试集应包含：

| 集合 | 目的 |
|---|---|
| 核心集 | 覆盖高频关键任务 |
| 边界集 | 缺参数、超长输入、空结果 |
| 故障集 | 超时、限流、工具部分失败 |
| 安全集 | 越权、注入、敏感信息 |
| 回归集 | 固化线上真实失败 |

每个样本需要输入、环境、验收器和允许的行为范围。开放任务可以有多条正确轨迹，不要只比较文本是否与标准答案一模一样。

## 评分方式

优先级一般是：

1. 确定性检查：测试、schema、数据状态、文件差异。
2. 规则检查：工具白名单、预算、必须步骤和禁止行为。
3. 模型评审：开放文本质量、证据完整度。
4. 人工审核：高风险样本和评分分歧。

模型评审要有明确 rubric，并用人工样本校准。不要让被评模型直接给自己打分。

## 线上监控

需要同时看平均值和分位数：

- 任务成功率与人工接管率。
- 首次成功率和恢复后成功率。
- P50/P95 总延迟。
- 每个成功任务的平均成本。
- 工具错误率与权限拒绝率。
- 无进展终止率。
- 用户取消率。

只优化单个指标可能产生反效果。例如减少工具调用数可能降低成功率，缩短输出可能丢失证据。

## 从失败到回归

```text
线上失败
  → 定位 trace
  → 复现环境
  → 判断根因类别
  → 修复 prompt / tool / runtime / policy
  → 加入回归集
  → 对比基线
  → 小流量发布
```

## 常见失败模式

- 只看最终回答，不看工具和权限轨迹。
- 只用几个 happy path 做演示。
- 测试环境的工具数据与生产差异巨大。
- 模型评审 rubric 含糊，分数无法解释。
- trace 没有版本信息，问题无法复现。
- 更新 prompt 后只看成功率，没有检查成本和延迟回退。

## 面试表达

我会把 Agent 运行保存为统一 trace，同时评估结果、轨迹、运行成本和安全行为。离线集覆盖正常、边界、故障、安全和线上回归样本；确定性校验优先，开放质量再使用模型评审。每次线上事故都要能从 trace 复现并沉淀为回归用例。
